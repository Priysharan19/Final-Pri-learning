# Auth email acceptance

**Evidence class: real Resend account and verified sender, real localhost HTTP server, Resend test sink inboxes; not the deployed service, not a human inbox.**

It does not show that a message reaches a person's inbox rather than their spam folder, how it renders in a mail client, or anything about Railway, Postgres or the deployed build.

## What it proves or disproves

Against a real `node server/index.js` on localhost that sends through the real Resend account:

| Step | Claim |
|---|---|
| 0 | `/v1/ready` reports `authEmail` ok, credential valid, sender domain verified — from the real provider, not from "the variables exist" |
| 1–2 | a code request for a new address is accepted by Resend from the configured sender; the stored message has the expected subject, body and single recipient; Resend's `last_event` reaches `delivered` |
| 3 | a wrong code is refused; the right code verifies; a session exists only afterwards; `/v1/handwriting/status` moves from 401 to an authenticated "not configured" answer |
| 4 | the same code a second time is refused |
| 5 | expiry is **not re-proved**: the server has no test seam for time. Cited from `server/test/otp-lifecycle-check.mjs` |
| 6 | sign out, then sign in again with a new code |
| 7 | a Class 10 child account is gated `GUARDIAN_CONSENT_PENDING`; the guardian's code email and link email are both accepted and delivered; a wrong guardian code approves nothing; the right one, through `/v1/account/otp/guardian/approve`, opens the gate |
| 8 | a send to `bounced@resend.dev`: what Resend reports and what the server told the client |
| 9 | a second server with a deliberately invalid key: `/v1/ready` says `AUTH_EMAIL_KEY_INVALID` (HTTP 200, degraded), a code request is an explicit `503 OTP_DELIVERY_FAILED`, and the log line carries the specific code |

Recipients are only Resend's documented test inboxes (`delivered+<label>@resend.dev`, `bounced+<label>@resend.dev`), with a random label per run. No real person is written to. One run requests 6 sends; the script stops itself at 14.

## Run

```bash
cd ~/Developer/Final-Pri-learning        # any directory linked to the Railway project
railway run --service Final-Pri-learning --environment production -- \
  node <path-to-this-checkout>/tools/acceptance/launch-auth-email.mjs
```

`--preflight` prints the variable names that would be passed and exits. Optional: `PRI_ACCEPT_OUT=<dir>` (scrubbed server logs and `auth-email-report.json`; default a temp directory), `PRI_ACCEPT_EXPECT_SENDER` (default `verify@mail.prilearning.com`).

Exit code: `0` every expectation met · `1` an expectation failed · `3` stopped at a stated limitation, or something is NOT VERIFIED · `2` a dependency is missing.

## What the launcher does with the credential

`railway run` injects the production service's variables into `launch-auth-email.mjs` only. The launcher:

- boots two local servers with a clean environment: `PATH`, `HOME`, `PRI_AUTH_EMAIL_PROVIDER`, `PRI_RESEND_API_KEY`, `PRI_AUTH_EMAIL_FROM`, and local settings (`NODE_ENV=development`, a temp SQLite file, a per-run `PRI_AUTH_DELIVERY_KEY`, `PRI_PUBLIC_ORIGIN` = the localhost origin). No database URL, Supabase, session, CSRF, handwriting, billing or SMS variable is passed, so production data cannot be reached. The second server gets a key generated by the launcher instead of the real one;
- runs `auth-email.mjs` in a clean child that receives the email key (and nothing else from Railway), because the only way to read a message sent to a test sink is Resend's own API;
- prints variable names only, and passes every byte of child output through a scrubber (key, bearer tokens, cookies, the local part of every address) before it reaches the terminal or a log file.

It never runs `railway variables`. With no credential it exits `2`, runs nothing and sends nothing. It never substitutes a mock.

## Codes, cookies, addresses

A verification code is read from Resend (`GET /emails/{id}`) into a local variable, used in the one request that spends it, and never printed, logged or written; the script's output scrubber knows every code it has read. Session cookies are never printed. Recipients are printed masked. Resend message ids are printed: they identify a message, not a person or a secret.

Message ids come from Resend's list endpoint (`GET /emails`), because the server does not expose the id of a code email. That list contains the account's other recent messages; they are dropped inside the filter that looks for this run's own recipients and nothing about them is kept or printed.

If the key is sending-only (`restricted_api_key`), Resend will not list or return sent messages. The script then stops, says exactly that, and exits `3`. It does not fake the loop.

## What it cannot show

- A bounce is reported by Resend after the send is accepted. The server consumes no Resend webhook, so the client is answered `202` for a bouncing address. Step 8 records this; it is a product gap, not a pass.
- Expiry (step 5), as above.
- The deployed service, Postgres, a human inbox, spam placement and rendering.
