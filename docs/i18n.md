# Interface languages

Pri Learning's interface is available in English and Hindi. The tutor's
captions and Pri Explain's narration follow the interface language too. This
page covers how that works, how to add a language, and how translations are
reviewed.

## What gets translated and what does not

| Translated (follows the language setting) | Not translated (English by design) |
| --- | --- |
| Buttons, menus, headings, status lines, errors, empty states | Question text, worked solutions, hints |
| Screen-reader labels (`aria-label`, `title`, `placeholder`, `alt`) | The marker's feedback and diagnoses |
| Pri Explain's own captions, statuses and checkpoint prompts | Syllabus chapter and subtopic names |
| Narration voice (en-IN / hi-IN) and how maths is *spoken* | NCERT topper notes and worked-example content |

The mathematics stays in English on purpose: JEE papers are English or
bilingual, and NTA treats the English as final wherever a translation is
ambiguous. The full reasoning is in the header of
`client/test/i18n-check.mjs`. For Hindi-medium students, the separate NCERT
term bridge (`client/src/i18n/glossary.js`, `ncertTerms.js`) shows the NCERT
Hindi term next to the English one. It never replaces the English.

## How it is built

- `client/src/i18n/languages.js` holds the `LANGUAGES` table. It is the only
  place a language is registered. Each entry gives the id, its name in its own
  script, the English name, the `<html lang>` value, the narration voice tags,
  the plural rule and a literal `import()` of its catalogue.
- `client/src/i18n/strings.en.js` is the source catalogue. Every key a screen
  uses lives here, and English is always in the entry chunk.
- `client/src/i18n/strings.<id>.js` holds one catalogue per other language. It
  must have exactly the English keys and import nothing. It is loaded with
  `import()` only when that language is chosen.
- `client/src/i18n/index.js` is the runtime: `useT()`, `useTx()` (for a
  sentence with a React node inside it), `translate()` (outside components) and
  `setLanguage()`. Its loaders come from the table.
- `client/vite.config.js` splits each catalogue into its own `i18n-<id>` chunk
  and keeps it out of the install precache. Both rules come from the table, so
  an English-only reader never downloads another language.
- `client/src/explain/speech.js` chooses the narration voice and turns maths
  into words in the narration language. For example, `x^2` is spoken as "x
  squared" in English and "x का वर्ग" in Hindi, and `\frac{3}{4}` as "3 divided
  by 4" or "3 बटा 4". It changes only what is spoken, never what is on the
  board.

### Voice selection

Narration asks for the language's registered tags in order (`en-IN`, then
`en-GB`, `en-AU`, `en-US` for English; `hi-IN` for Hindi). If none is
installed, it uses any voice of the same base language. If there is none of
those either, it falls back to English. It never chooses a voice of an
unrelated language. When the browser has not listed its voices yet, the
utterance is still tagged with the language, so the platform can pick a voice
itself. On-device voices are preferred because they keep working offline.

## Adding a language (for example Marathi or Tamil)

1. Copy `client/src/i18n/strings.hi.js` to `strings.<id>.js` (for example
   `strings.mr.js`) and translate every value. Keep every `{placeholder}`
   exactly as it is, and give each counted string both its `one` and `other`
   forms.
2. Add one entry to `LANGUAGES` in `client/src/i18n/languages.js`:

   ```js
   {
     id: 'mr', label: 'मराठी', english: 'Marathi', htmlLang: 'mr',
     speech: ['mr-IN'],
     // plural: omit to use Intl.PluralRules('mr'); every catalogue entry
     // carries only `one` and `other`, so a language needing more forms must
     // grow the catalogue shape first.
     load: () => import('./strings.mr.js').then(m => m.default)
   }
   ```

3. Run `npm run test:i18n`. It fails if any key is missing or extra, if a
   placeholder was dropped, or if the build has not split the new catalogue
   out of the install.
4. If the language has its own maths-speech conventions, add a word table for
   it in `client/src/explain/speech.js`. Without one, maths is spoken with the
   English words.

Nothing else needs to change. The settings switch, the sign-in language picker,
`<html lang>`, the build chunk, the service-worker rule and the narration voice
all read the table.

## Adding a string

- Put the English in `strings.en.js` and the translation in every other
  catalogue under the same key, then call `t('ns.key', { …vars })`.
- One sentence is one key. Never build a sentence from fragments, and never
  pluralise with a trailing `s`. Use `{ one, other }` and pass `count`.
- Pass every placeholder the English template names.
  `client/test/i18n-coverage-check.mjs` checks every call site that it can
  resolve statically.
- No page or component may hard-code user-visible English. The coverage check
  parses every file under `src/pages`, `src/components` and `src/ink` (the
  handwriting workspace and calibration) and fails on any
  text node, prose string, template literal or spoken attribute that bypasses
  `t()`. Exceptions are explicit:
  - `client/test/i18n-hardcoded-allowlist.json` has two lists. `files` is for a
    whole file that is not student or teacher interface, such as a staff
    console or a hidden device-study harness. `literals` is for exact strings
    that are the same in every language, such as the product name. Every entry
    needs a written reason.
  - `// i18n-exempt-start: <reason>` … `// i18n-exempt-end` marks a region of
    authored mathematics content, such as NCERT topper notes or worked
    examples. It may not be used on the core student screens.

## Translation review policy

- Hindi follows the register of NCERT's Hindi-medium mathematics books. It
  uses आप, `-ें` imperatives on controls (सहेजें, जारी रखें) and `-इए` in
  instructions (कीजिए). Terms are NCERT's: प्रश्न, उत्तर, हल, प्रश्नावली,
  अध्याय, अंक. The header of `strings.hi.js` lists the sources used to settle
  terminology.
- Proper names (Pri, NCERT, CBSE, JEE, IOQM) stay in Latin script.
- Machine-authored translations must say so in the PR that introduces them.
  They are **not** considered reviewed until a native speaker who knows the
  school register has read them on screen. Record that review in the PR or a
  follow-up issue. Do not claim it in advance.
- A PR may not weaken the coverage check, the allowlists or the parity checks
  to make a translation gap pass. Translate the string instead.
- Synthetic test evidence, such as the `tour-hindi.js` browser flow, shows
  that the screens render the catalogue. It does not show that the Hindi is
  good. Treat those as two separate claims.

## Tests

| Suite | What it holds |
| --- | --- |
| `client/test/i18n-check.mjs` | Catalogue contract, Hindi-only allowlist, lazy loading, plural rules, NCERT term bridge, no work lost on switch |
| `client/test/i18n-coverage-check.mjs` | No hard-coded English in any page or component, placeholders passed at every call site, key parity for every registered language |
| `client/test/i18n-voice-check.mjs` | Narration voice per language with fallbacks, maths spoken in each language, one registration table |
| `client/test/tour-hindi.js` | Browser: a Hindi profile visits Home, Practice, the handwriting workspace (toolbar, reading panel, symbol picker), feedback, Explain, Exams, an exam room, Progress and Settings with no English fallback on screen |
