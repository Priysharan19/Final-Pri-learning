**Status:** engineering runbook, 2026-10-19. Nothing here has been done in Play Console. Every
Console step is the **OWNER's**, in the owner's own browser; engineering prepares the bundle, the
listing (`play-listing.md`), the graphics (`play/`) and the Data safety answers
(`../play-data-safety.md`). Play's rules change: where this file states a Play rule, confirm the
current wording in Play Console before relying on it.

## 1. One-time setup (OWNER)

1. **Developer account type.** Confirm whether the account is *personal* or *organisation*. A
   personal account created after November 2023 must run a closed test with **at least 12
   testers opted in continuously for the last 14 days** before it can apply for production
   access (Play's rule as of this writing — confirm in Console → Dashboard). An organisation
   account does not have this requirement.
2. **Create the app**: name `Pri Learning: Maths Practice`, default language English (India),
   App, Free (with in-app subscriptions). Package name is fixed by the first upload:
   `com.prilearning.app` (`android/app/build.gradle.kts` `applicationId`) — it can never change.
3. **Play App Signing**: accept Google-managed app signing on the first upload. Our key is the
   **upload key** only. If Console asks for the upload certificate, its SHA-256 is printed by
   `create-upload-key.sh` and by every `build-release-aab.sh` run.
   - Lost upload key: Play support can reset it; the app signing key is never ours to lose.
   - After the first upload, copy the **app signing key** SHA-256 from Console → Test and release
     → App integrity. The cloud's `/.well-known/assetlinks.json` (App Links for account actions)
     must name *that* fingerprint, not the upload key's.
4. **Play Billing**: create the subscription products and prices (₹199 / month, ₹1,499 / year;
   `PRI_V1_RELEASE_SCOPE.md`), add the testers' Google accounts as **licence testers** (Console →
   Settings → License testing) so test purchases are not charged, and set the server's Google
   Play billing environment (`server/platform/googleBilling.js`) on the cloud.
5. **App content** declarations: privacy policy URL, ads (No), app access (reviewer account and
   instructions), content rating (IARC, `play-listing.md` §3), target audience (**OWNER /
   counsel**, `play-listing.md` §5), Data safety (`../play-data-safety.md` §7), government app
   (No), financial features (No), health (No).

## 2. Build an upload

```bash
android/scripts/build-release-aab.sh 1 https://<production-cloud-origin>
```

- `versionCode` must be a positive integer strictly greater than every code already uploaded to
  any track (Play rejects reuse). Keep a record in the release log: versionCode → commit SHA →
  bundle SHA-256 (all three printed by the script).
- The web product inside the bundle carries the commit's release identity
  (`client/dist/release.json`); a dirty tree is refused so the bundle and the commit agree.
- Before uploading, install the same commit's release build on at least one phone and one tablet
  and run the device checks in `docs/release/evidence/device-matrix/README.md`. Synthetic and
  emulator evidence is recorded separately from physical-device evidence.

## 3. Internal testing (first)

1. Console → Test and release → Testing → **Internal testing** → Create release → upload the AAB.
2. Testers: an email list of the owner's own accounts (up to 100). Share the opt-in link.
3. Install from the Play opt-in link (not by sideloading) and check: sign-in, a marked practice
   answer online, the offline refusal (nothing marked offline), a licence-test subscription
   purchase, restore, cancel, and account deletion.
4. Fix and re-upload with a higher versionCode as often as needed.

## 4. Closed testing — the 12 testers × 14 days gate (personal accounts)

1. Console → Closed testing → create a track (e.g. `closed-alpha`) → upload the same or a newer
   AAB → countries: India (add others only deliberately).
2. **Testers**: a Google Group or email list of **at least 12 real people** (aim for 15–20 so a
   drop-out does not reset the count). They must be real users who opt in through the link and
   install from Play; Play counts *opted-in* testers, and the 14 days must be **continuous**.
   - Never use fabricated, duplicate or purchased tester accounts — that breaks Play policy and
     our evidence rules (`AGENTS.md`: never fabricate student, teacher or human-review evidence).
   - Testers under 18 need a parent or guardian to confirm their Pri account before answers are
     checked; prefer adult testers (parents, teachers, older students) for the gate.
3. **Keep a log** (outside the repository if it contains personal data): date each tester opted
   in, device model, Android version. The production-access application asks how testing went
   and what changed, so record feedback and the versions shipped during the 14 days.
4. Ship at least one update during the test in response to feedback (a higher versionCode on the
   same track); Play's questionnaire asks about this.
5. **Day 15 or later**, with ≥ 12 testers continuously opted in for the last 14 days: Console →
   Dashboard → **Apply for production access**, answer the questionnaire truthfully. Review can
   take several days.

## 5. Production

1. After access is granted: Production → Create release → promote the closed-test AAB or upload
   a newer one.
2. Use a **staged rollout** (e.g. 5 % → 20 % → 50 % → 100 %), watching the server's ops alerts and
   the Play Console vitals between steps. Halting a staged rollout is available; a released
   versionCode can never be reused.
3. Release notes: factual changes only (same truthfulness rules as the listing).

## 6. Things that block a release (check before every upload)

- `node tools/play-listing-check.mjs`, `node tools/play-data-safety-check.mjs` pass.
- The Android shell suite passes (`.github/workflows/android-shell.yml`).
- Data safety, privacy policy and the in-app notice describe the same data flows (change all of
  them together — `../play-data-safety.md` header).
- Google Play Billing certification items in `PRI_V1_RELEASE_SCOPE.md` §22.2 are closed.
- Legal / privacy sign-off (counsel pack) for the target-audience and Families-policy answers.
